# Regras de Negócio

Base: RFC original em https://github.com/LucasKlemke/PAC-Extensionista-VII---RFC---CRM-Advocacia (seção 2.5), evoluído para **multi-tenant com cadastro de usuários**. Cada regra aponta o Service responsável — ver [../arquitetura/visao-geral.md](../arquitetura/visao-geral.md) e [../database/schema.md](../database/schema.md). Regras marcadas **(revisada)** mudam o comportamento do RFC original; **(nova)** não existiam no RFC original.

## Autenticação, Tenants e Usuários

- **RN01** — Apenas usuários autenticados acessam qualquer recurso; sem sessão válida → redirect para login. *(`AuthMiddleware`)*
- **RN02 (revisada 2)** — Sistema é multi-tenant com usuário podendo pertencer a N escritórios: cadastro é self-service e coleta só nome/e-mail/senha, criando um `usuario` (perfil global). Se havia `convite` pendente para o e-mail, o cadastro já cria a(s) membership(s) correspondente(s) (role do convite) na mesma transação; senão o usuário segue para o onboarding, que cria seu primeiro `escritorio` e o torna `owner` dele via `membro`. *(`UsuarioService`, `EscritorioService`, tabelas `escritorio` + `usuario` + `membro` + `convite`)*
  - No RFC original (RN02), o sistema era monousuário com usuário único provisionado via configuração de ambiente — não havia cadastro pela UI, nem múltiplos escritórios por usuário.
  - Evolução sobre a primeira revisão: `usuario` deixou de ter `escritorio_id`/`role` fixos — a associação usuário↔escritório com papel vive em `membro` (N:N), permitindo um mesmo profissional participar de vários escritórios com papéis diferentes. O escritório ativo da sessão é trocável (switcher no header) e sempre revalidado contra `membro` no banco, nunca confiado a partir do payload do client.
- **RN02a (revisada)** — Papéis por escritório seguem a hierarquia `owner > admin > padrao` (substitui `titular`/`colaborador`). `owner`/`admin` convidam/gerenciam membros; `padrao` não gerencia ninguém. Um ator só altera/remove um membro de nível estritamente menor — exceto `owner`, que também gerencia outro `owner` (a proteção real é RN02c). Só `owner` promove alguém a `owner`. Auto-alteração/auto-remoção do próprio papel é bloqueada. *(`MembroService`, `permissoes.ts`)*
- **RN02b** — O e-mail de um usuário é único globalmente na plataforma (identidade de login); um mesmo e-mail nunca cria dois perfis `usuario` — pode, porém, ter memberships (via `membro`) em vários escritórios diferentes. *(`UsuarioService`, constraint `@unique` em `usuario.email`)*
- **RN02c (nova)** — Um escritório nunca fica sem nenhum `owner`: rebaixar ou remover o último `owner` de um escritório é bloqueado. *(`MembroService`)*
- **RN03** — Sessão expira após inatividade, exigindo novo login. *(`AuthMiddleware` / NextAuth.js)*
- **RN19 (nova)** — Isolamento de tenant: nenhuma operação de leitura ou escrita pode acessar/alterar dados de um `escritorio_id` diferente do usuário autenticado na sessão. Toda query de Repository é obrigatoriamente escopada por `escritorio_id` (direto ou via join até `caso`/`cliente`). Violação é tratada como bug de segurança crítico, não como validação de negócio comum. *(todos os Repositories — ver [../arquitetura/visao-geral.md#isolamento-de-tenant-defesa-em-profundidade](../arquitetura/visao-geral.md#isolamento-de-tenant-defesa-em-profundidade))*

## Gestão de Clientes

- **RN04 (revisada)** — Cliente nunca é excluído permanentemente: "desativar" grava a data em `cliente.soft_deleted_at` (soft delete), e cliente ativo é simplesmente `soft_deleted_at IS NULL`. O cadastro e todo o histórico vinculado (casos, comentários, mensagens) são preservados, e a operação é reversível por "Restaurar". A listagem omite os desativados por padrão, com filtro explícito para exibi-los. *(`ClienteService`)*
- **RN05 (revisada)** — CPF único **dentro do mesmo escritório**; o mesmo CPF pode existir em escritórios diferentes (são tenants distintos). Bloquear apenas duplicidade dentro do próprio tenant. *(`ClienteService`, constraint composta `@@unique([escritorio_id, cpf])`)*
  - No RFC original, o CPF era único globalmente — fazia sentido em um sistema de usuário único.
- **RN05a (nova)** — CPF, telefone e e-mail do cliente são validados no cadastro e na edição: CPF pelos dígitos verificadores, telefone como celular brasileiro completo (`+55` + DDD + nono dígito) e e-mail pela forma. Campo opcional em branco continua válido; preenchido, precisa estar correto — um telefone incompleto só apareceria como falha na hora do disparo de WhatsApp (RN13). Armazenados sem máscara; a formatação é de apresentação. *(`ClienteService` + schemas zod das rotas)*
- **RN06** — Todo caso deve pertencer a um cliente existente, ativo (não desativado), e do mesmo escritório do usuário logado; um cliente inativo não pode ser vinculado a um caso novo nem a um já existente. *(`CasoService`)*

## Gestão de Casos

- **RN07** — Caso sempre pertence a um `status` do escritório; nunca existe fora do kanban. *(`CasoService`)*
- **RN08** — Casos arquivados saem do pipeline ativo (kanban e tabela mostram só ativos por padrão), mas continuam acessíveis no histórico do cliente/escritório; um caso nunca é excluído de fato. *(`CasoService`)*
- **RN09** — Exclusão de um `status` só é permitida se não houver casos vinculados a ele (`onDelete: Restrict` no banco garante isso mesmo com bug de aplicação); qualquer usuário do escritório com papel de gestão (`owner`/`admin`) pode mover os casos e então remover a coluna — não é restrito ao titular. *(`StatusService`)*

## Prazos e Lembretes

- **RN10** — Prazo sempre vinculado a um caso existente; não é permitido prazo solto. *(`PrazoService`)*
- **RN11** — Prazo com data anterior à atual não pode ser cadastrado como futuro; deve ser registrado como retroativo com indicação visual de atraso. *(`PrazoService`, campo `prazo.retroativo`)*
- **RN12** — Notificações de prazo (3 dias antes, 1 dia antes, no dia) são automáticas, sem ação manual, para todos os escritórios ativos. *(`NotificacaoScheduler`, tabela `notificacoes_prazo`)*

## Disparo de Mensagens via WhatsApp

- **RN13** — Disparo só é permitido para cliente com telefone cadastrado; sistema deve alertar se o campo estiver vazio. *(`MensagemService`)*
- **RN14** — Mensagens agendadas são processadas em segundo plano por serviço assíncrono (AWS Lambda), iterando por todos os escritórios; nenhum usuário precisa estar com a interface aberta. *(`NotificacaoScheduler`)*
- **RN15** — Todo disparo (sucesso ou falha) é registrado no histórico do cliente com data, hora, conteúdo e usuário que disparou (quando manual). *(`MensagemService`, tabela `historico_mensagem`)*
- **RN16** — Em caso de falha, até 3 tentativas automáticas antes de registrar erro definitivo. *(`MensagemService` / `UazapiClient`, campo `historico_mensagem.tentativas`)*
- **RN16a (nova)** — Templates de mensagem (`template_mensagem`) são compartilhados entre todos os usuários de um mesmo escritório; um colaborador pode usar/editar templates criados pelo titular e vice-versa. *(`MensagemService`)*

### Campanhas (disparo em massa)

- **RN23 (nova)** — Uma campanha só pode ser criada a partir de uma instância de WhatsApp **conectada** do próprio escritório; instância desconectada, hibernada ou de outro tenant recusa a criação antes de qualquer efeito. *(`CampanhaService`)*
- **RN24 (nova)** — Toda `{{variavel}}` da mensagem-modelo precisa estar mapeada para uma coluna existente da planilha. O sistema tenta casar sozinho pelo nome (ignorando caixa, acento e separadores: `{{nome_completo}}` acha a coluna "Nome Completo"); o que não casar é escolhido explicitamente pelo usuário antes de criar. Nenhuma mensagem sai com o placeholder cru. *(`CampanhaService`, `lib/utils/campanha-mensagem`)*
- **RN24a (nova)** — Cada variável pode receber uma **cadeia ordenada de tratamentos** aplicada ao valor da célula antes de ele entrar na mensagem (só o primeiro nome, só o último nome, primeiro e último, maiúscula em cada nome, maiúscula só no primeiro, TUDO MAIÚSCULO, tudo minúsculo, remover acentos). A cadeia roda na ordem escolhida, então "maiúscula apenas no primeiro nome" sai da combinação e não precisa de um tratamento dedicado. Tratamento desconhecido (campanha antiga, payload adulterado) é ignorado em vez de quebrar a renderização. *(`lib/utils/campanha-tratamentos`)*
- **RN24b (nova)** — Cada variável pode ter um **valor padrão** usado quando o resultado fica vazio, evitando mensagem com buraco ("Olá, !") quando a planilha tem célula em branco. O padrão é o texto final: os tratamentos não são reaplicados sobre ele. *(`lib/utils/campanha-mensagem`)*
- **RN25 (nova)** — Toda linha da planilha precisa de um número de WhatsApp válido (DDI + DDD + 9 dígitos, mesma validação de `cliente.telefone` — RN13). Havendo qualquer número inválido, **a campanha inteira é recusada** com a indicação das linhas com problema: enviar só parte da lista sem o usuário perceber é pior do que recusar e deixar corrigir a planilha. *(`CampanhaService`)*
- **RN26 (nova)** — Criar, pausar, retomar e excluir campanha é restrito a `owner`/`admin`; `padrao` apenas lê e sincroniza (sincronizar é leitura de estado). *(`CampanhaService`)*
- **RN27 (nova)** — A mensagem de cada destinatário é renderizada **no servidor** a partir das linhas cruas do CSV e gravada em `campanha_item` como snapshot imutável — o cliente nunca envia texto já renderizado, e o registro reflete exatamente o que foi entregue à UAZAPI. *(`CampanhaService`)*
- **RN29 (nova)** — O status de cada mensagem da campanha (pendente, enviada, entregue, lida, falha) **não é espelhado no banco**: é consultado ao vivo na UAZAPI (`POST /sender/listmessages`) quando a campanha é aberta, depois que os destinatários gravados já estão na tela. O casamento é pelo número de destino, normalizado dos dois lados porque o WhatsApp devolve o celular brasileiro **sem o nono dígito** (`554797355799@s.whatsapp.net`) enquanto o CRM grava com ele (RN13); destinatário sem mensagem correspondente aparece em branco, nunca como "pendente" — inventar estado seria pior do que admitir que não se sabe. Falha na consulta não derruba a tela: a tabela do banco continua visível. O casamento acontece **no servidor**: a página aberta define quais números interessam e só o status deles trafega até o browser, que antes recebia a campanha inteira para desenhar 50 linhas. A janela pedida à UAZAPI é dimensionada pela **campanha**, nunca pela página — a ordem devolvida por ela não acompanha a das linhas do CSV (o delay é sorteado e há retentativas) e o mesmo número pode repetir em linhas diferentes, então recortar por página faria destinatário real aparecer sem status. O `limit` é sempre explícito, porque o endpoint tem teto próprio; quando ainda assim a resposta vem cortada, a tela diz isso em vez de deixar o vazio passar por "mensagem não enviada". *(`CampanhaService`, `lib/utils/campanha-status-mensagem`)*
- **RN28 (nova)** — A UAZAPI é a dona do envio: o estado local só muda depois que ela aceita a operação. Sincronizar não escreve nem gera log quando nenhum contador ou status mudou, e excluir remove a campanha localmente apenas após a confirmação, preservando o rastro em `log` (append-only). *(`CampanhaService`)*
- **RN30 (nova)** — Uma `instancia_whatsapp` **nunca é apagada fisicamente**: excluir grava `soft_deleted_at` (ativa = `NULL`), como em `cliente` (RN04). A linha é a única cópia do `uazapi_token`, e sem ela toda campanha daquela instância perde o canal de controle com a UAZAPI — não pode mais ser sincronizada, pausada nem excluída. Isso vale para os dois caminhos de exclusão: o manual (owner/admin, depois que a UAZAPI confirma) e o automático da sincronização, que marca a instância ausente de `/instance/all` em vez de removê-la. A marcação do sync é **reversível**: a instância que reaparece na UAZAPI é restaurada, para que uma resposta parcial ou um servidor mal configurado não vire perda permanente de acesso. O nome continua reservado pela instância excluída (o `@@unique` a abrange), o que torna a restauração segura e faz o cadastro de uma instância homônima ser recusado com essa explicação. Instância excluída some das listagens e recusa reconectar/desconectar/verificar/excluir, mas continua resolvendo o token para o histórico das campanhas — e **não** pode disparar campanha nova, ainda que seu último status conhecido seja `connected`. *(`InstanciaWhatsappService`, `CampanhaService`)*

## Documentos

- **RN17** — Tamanho máximo por arquivo: 10 MB. *(`DocumentoService`, campo `documento.tamanho_kb`)*
- **RN18** — Tipos aceitos: PDF, DOCX, JPG, PNG, JPEG; outros formatos rejeitados com mensagem de erro clara. *(`DocumentoService`)*

## Auditoria e comentários

- **RN20 (nova)** — Toda operação de escrita do sistema gera um registro em `log` respondendo três perguntas: **quem fez** (`usuario_id`), **quando fez** (`created_at`) e **o que fez** (`acao` + `entidade` + `entidade_id` + `resumo`, com o diff dos campos alterados em `dados`). O log é gravado na **mesma transação** da mudança que o originou — uma escrita que falha não deixa log órfão, e um log existente sempre corresponde a uma mudança efetivada. Atualização que não altera nenhum campo não gera log. A tabela é *append-only*: não há update nem delete de registro de auditoria. *(`LogService`, tabela `log`)*
- **RN21 (nova)** — Comentários substituem o campo livre de observações e são ancorados a uma entidade por `(escopo, escopo_id)` — hoje `cliente` e `caso`, extensível a prazos sem tabela nova. Como não há FK para o alvo, o Service valida que o alvo pertence ao escritório da sessão antes de ancorar o comentário (RN19). Editar o texto é exclusivo do autor (nem `owner` edita fala alheia); excluir é moderação e cabe ao autor, `owner` ou `admin`. Exclusão é soft delete, e toda operação sobre comentário alimenta o `log` (RN20). *(`ComentarioService`, tabela `comentario`)*
- **RN22 (nova)** — Todo caso tem um **tipo de processo** obrigatório (`tipo_processo`), cadastrado pelo próprio escritório em `/configuracoes/tipos-processo` com nome, cor e ícone — exatamente como um `status`. O tipo substituiu o antigo `caso.titulo` (texto livre): o título não era padronizado, o que impedia agrupar, filtrar e comparar processos pela sua natureza. O nome é único por escritório, e a escrita (criar/editar/excluir) é restrita a `owner`/`admin`, como a de `status` — o papel `padrao` escolhe entre os tipos existentes, mas não cria. Um tipo com processos vinculados **não pode ser excluído** (mesma proteção de RN09 para status: checagem amigável no Service + `onDelete: Restrict` como rede de segurança). Escritório novo nasce com um conjunto inicial de tipos, senão não seria possível cadastrar o primeiro processo. *(`TipoProcessoService`, tabela `tipo_processo`)*

## Agenda

Módulo novo (rota `/agenda`), independente do módulo de prazos do RFC (RN10–RN12, ainda não implementado): um calendário do escritório, com visões de mês, semana e dia, para marcar audiências, reuniões e compromissos. RN19 e RN20 valem integralmente — toda query é escopada por `escritorio_id` e toda escrita grava `log` com entidade `evento` na mesma transação.

- **RN31 (nova)** — A agenda é **compartilhada por todo o escritório**: qualquer membro (inclusive `padrao`) vê todos os eventos do tenant e pode criar evento novo. Um escritório de advocacia coordena audiência e reunião em equipe — uma agenda por usuário exigiria duplicar o mesmo compromisso para cada pessoa envolvida, e a visibilidade compartilhada é justamente o que o Dr. Lucas Quintino não tem hoje espalhando compromissos em WhatsApp. O evento pode ter um **vínculo opcional e exclusivo**: `caso_id` **ou** `cliente_id`, **nunca os dois**, e legitimamente nenhum dos dois (reunião interna, prazo administrativo). A exclusividade é mais honesta do que aceitar os dois: o caso já resolve o cliente, então um evento com os dois campos permitiria apontar para um caso de um cliente e para outro cliente ao mesmo tempo. O alvo (caso ou cliente) é validado contra o escritório da sessão antes de qualquer escrita, como faz `comentario` (RN21). *(`EventoService`, tabela `evento`)*
- **RN32 (nova)** — Todo evento tem uma `modalidade` obrigatória que determina qual campo de endereço é exigido: `presencial` exige `local` (fórum, sala, endereço) e `online` exige `link_reuniao`. O campo da modalidade **não** escolhida é gravado como `NULL`, nunca guardado "por precaução" — um evento online com endereço de fórum remanescente de uma edição anterior mandaria a pessoa para o lugar errado, e o campo vazio é a única representação verdadeira de "não se aplica". A troca de modalidade na edição, portanto, limpa o campo antigo. *(`EventoService`, tabela `evento`)*
- **RN33 (nova)** — Participantes de um evento são **membros do próprio escritório** (validados contra `membro` do tenant, RN19), nunca e-mails livres: a agenda não é ferramenta de convite externo, e um participante que não é membro não conseguiria abrir o evento de que faz parte. O **criador entra automaticamente como participante** e não pode ser removido enquanto for o autor — ele responde pelo compromisso e é quem pode editá-lo (RN34); deixá-lo fora da própria lista tornaria o evento órfão de responsável. O conjunto de participantes é único por evento (`@@unique([evento_id, membro_id])`), e editar participantes é substituir o conjunto, não versionar linha por linha. *(`EventoService`, tabelas `evento` + `evento_participante`)*
- **RN34 (nova)** — Editar e excluir evento é permitido ao **autor, `owner` ou `admin`** — exatamente a regra de moderação de comentários (RN21, `podeModerarComentario` em `src/lib/auth/permissoes.ts`), reaproveitada em vez de reinventada: a agenda é compartilhada para leitura, mas mexer no compromisso alheio é ato de gestão. Excluir é **soft delete** (`soft_deleted_at`, ativo = `NULL`), como em `cliente` (RN04) e `instancia_whatsapp` (RN30): a agenda e toda contagem listam somente `soft_deleted_at IS NULL`, e o histórico de quem marcou e desmarcou o quê sobrevive no `log` (RN20) com a linha ainda referenciável. *(`EventoService`, tabela `evento`)*
- **RN35 (nova)** — `fim` precisa ser **estritamente posterior** a `inicio`; evento de duração zero ou invertida é recusado na criação e na edição, porque nenhuma das três visões do calendário sabe desenhá-lo. Evento de **dia inteiro** (`dia_inteiro = true`) é normalizado no servidor para 00:00:00.000 do dia de início até 23:59:59.999 do dia de fim, e não para o dia seguinte — assim ele ocupa exatamente os dias que o usuário marcou, sem transbordar uma coluna a mais na visão de semana. Data no **passado é permitida**, sem alerta bloqueante: registrar retrospectivamente uma audiência já realizada é uso legítimo, e aqui não existe o conceito de "retroativo" de RN11, que é do módulo de prazos. **Fora de escopo nesta versão**, explicitamente: **recorrência** (evento repetido gera linhas independentes) e **notificações/lembretes** de evento — o `NotificacaoScheduler` cuida de prazos (RN12), não de agenda. *(`EventoService`, tabela `evento`)*

## Requisitos não funcionais que afetam regras de negócio

- **RNF03/RNF04/RNF05** — Autenticação JWT (com `escritorioId` + `role` embutidos), senha com bcrypt, tudo via HTTPS.
- **RNF06** — Dados sensíveis do cliente (CPF, telefone, dados processuais) tratados em conformidade com a LGPD, isolados por escritório.
- **RNF09** — Sistema deve suportar até 1.000 clientes e 5.000 casos **por escritório**, com o número de escritórios podendo crescer sem degradação (índices compostos por `escritorio_id`).
- **RNF11/RNF13** — Uso autônomo após treinamento breve; localizar informação de cliente em menos de 30s.

## Fluxos alternativos relevantes

Derivados dos fluxos principais (cadastro de escritório, login, convite de colaborador, cadastro de cliente, cadastro de caso):

- **FA-01** — Login com credenciais inválidas → mensagem de erro, permanece na tela.
- **FA-02** — Cancelamento do cadastro de cliente → modal fecha sem salvar.
- **FA-03** — CPF já cadastrado **no mesmo escritório** → erro de duplicidade, modal permanece aberto (aplica RN05 revisada).
- **FA-03a (nova)** — CPF pertence a um cliente **desativado** do mesmo escritório → erro específico orientando restaurar o cadastro existente em vez de criar outro (aplica RN04 + RN05).
- **FA-04** — Cancelamento do cadastro de caso → modal fecha sem criar.
- **FA-05** — Tentativa de criar caso sem cliente selecionado → validação de campo obrigatório, não prossegue (aplica RN06).
- **FA-06 (nova)** — Cadastro com e-mail já usado por outro usuário → erro de duplicidade, cadastro não prossegue (aplica RN02b).
- **FA-07 (nova)** — Membro `padrao` tenta convidar/gerenciar outro membro → ação bloqueada (403), a UI esconde as ações de gestão (aplica RN02a).
- **FA-08 (nova)** — Usuário autenticado tenta acessar (via URL direta ou manipulação de request) um recurso de outro escritório → sistema retorna 404, sem confirmar existência do recurso (aplica RN19).
- **FA-09 (nova)** — Ação em lote recebe ids de clientes de outro escritório ou já desativados → esses ids são silenciosamente descartados e contados como ignorados; apenas os alvos legítimos são afetados (aplica RN19 + RN04).
- **FA-10 (nova)** — Usuário tenta editar comentário de outra pessoa → ação bloqueada (403) e a UI não oferece a opção (aplica RN21).
- **FA-11 (nova)** — Escritório tenta excluir um tipo de processo que ainda tem processos vinculados → ação recusada (409) com mensagem explicando o motivo, o tipo permanece na lista (aplica RN22).
- **FA-12 (nova)** — Usuário precisa de um tipo que ainda não existe ao cadastrar um processo → usa o atalho "Criar tipo" dentro do próprio formulário, e o tipo recém-criado já vem selecionado (o atalho não aparece para o papel `padrao`, que não pode configurar o escritório — aplica RN22).
- **FA-13 (nova)** — Evento é criado/editado apontando para um caso ou cliente de outro escritório → sistema retorna 404, sem confirmar a existência do alvo, e o evento não é gravado (aplica RN19 + RN31).
- **FA-14 (nova)** — Evento é enviado com `fim` menor ou igual a `inicio` → validação recusa com 422 e a mensagem indica qual campo corrigir; nada é gravado (aplica RN35).
- **FA-15 (nova)** — Evento é enviado com `caso_id` e `cliente_id` preenchidos ao mesmo tempo → recusado com 422 explicando que o vínculo é exclusivo; a UI oferece um único seletor de vínculo, então isso só acontece por request manipulado (aplica RN31).
- **FA-16 (nova)** — Membro que não é o autor nem `owner`/`admin` tenta editar ou excluir um evento → ação bloqueada (403) e a UI não oferece as ações no evento alheio; ele continua vendo o evento normalmente na agenda (aplica RN34).
